# CraftSpirits Simulator

Симулятор куба+колонны+узла отбора (LM) для dry-run проверки логики стейт-машины
перед сборкой реального железа.

## Что моделирует

- **Физика**: тепловой баланс куба, кипение бинарной смеси этанол-вода (Antoine),
  обогащение пара в колонне с инерцией ~90 сек, конденсация на обратном
  холодильнике, тепловой баланс охлаждающей воды
- **Хардвер**: GPIO-выходы ESP (heater PWM, valve_takeoff, valve_water, contactor),
  «чтение датчиков» (с поддержкой fault-injection NaN)
- **Контроллер**: стейт-машина для LM-ректификации (INIT → HEAT_UP → STABILIZE →
  HEADS → STABILIZE2 → BODY → TAILS → SHUTDOWN), потстил, ШИМ узла отбора,
  барокоррекция, tripwires по T_water_out, watchdog, emergency-handling
- **Fault injection** для проверки safety:
  - обрыв любого датчика → NaN
  - залипание клапана узла отбора OPEN/CLOSED
  - пробой SSR ТЭНа (нагрев 100 % независимо от команды)
  - закрытый кран воды (нет потока несмотря на открытый соленоид)
  - E-stop / биметалл / термопред
  - отключение Pi → ESP-watchdog должен сработать через 30 сек

## Что в UI

- **Большие индикаторы** температур (T_kub, T_head, T_water_in, T_water_out)
  с цветовой кодировкой и подсветкой `SENSOR FAIL` при NaN
- **Фаза процесса** — большой цветной тег (HEAT_UP/HEADS/BODY/TAILS/...)
- **Выходы железа** — мощность ТЭНа (полоса), LED-индикаторы клапанов и контактора,
  текущий duty cycle ШИМ узла отбора
- **График** последних 30 мин sim-времени: T_kub (красная), T_head (оранжевая),
  T_water_out (синяя)
- **Статистика**: объём куба, крепость браги, V продукта, его крепость, состав
  пара наверху, мощность на пар, давление атм.
- **Управление**:
  - Старт сессии с параметрами рецепта (V, крепость, мощность, duty cycles, время стабилизации)
  - Стоп / Пауза / Reset
  - Скорость симуляции ×0.1 ... ×600 (×60 = час за минуту, удобно для длинных фаз)
- **Fault injection panel** — клик включает/выключает соответствующую неисправность
- **Лог** переходов и алертов

## Типовой сценарий проверки

1. Поставить скорость ×60
2. Стартовать сессию REFLUX с дефолтами (18 L браги 12 %, p_work 60 %)
3. Наблюдать:
   - HEAT_UP: куб греется, T_kub растёт до точки кипения смеси (~82 °C)
   - При T_head > 78 °C переход в STABILIZE
   - STABILIZE 10 мин — клапан закрыт, total reflux
   - HEADS — ШИМ клапана с низким duty 15 %, объём продукта растёт медленно
   - При T_kub > 88 °C → STABILIZE2 → BODY
   - BODY — основной отбор, duty 40 %
   - При T_head поднимется выше 78.5 °C (хвосты пробились) → TAILS
   - TAILS до T_kub > 99 °C → SHUTDOWN → DONE
4. Проверить safety: на любом этапе включить «E-stop» → должен быть мгновенный EMERGENCY
5. Включить «Pi disconnected» → через 30 сек sim-time должен сработать watchdog

## Headless тесты

```bash
python tests.py
```

10 сценариев в CI-стиле, exit 0 если все зелёные. Покрывают:

1. Happy path REFLUX 18L@12 % — все фазы пройдены, продукт в разумных границах
2. E-stop в HEAT_UP — EMERGENCY мгновенный
3. Watchdog (Pi disconnect) — EMERGENCY за ≤30 сек
4. Отказ датчика T_kub — EMERGENCY
5. Закрытый кран воды — EMERGENCY по T_water_out
6. Пробой SSR ТЭНа — PZEM-style detection срабатывает (cmd vs measured power)
7. Acknowledge emergency → IDLE
8. POTSTILL без разделения — клапан узла отбора открыт всю фазу BODY
9. Шум датчиков ±0.5°C — стейт-машина не дёргается
10. Дрейф атм. давления ±10 hPa — барокоррекция держит логику стабильной

## Известные ограничения модели

Намеренные упрощения, которые могут расходиться с реальностью:

| Аспект | Что упрощено | Влияние |
|---|---|---|
| VLE этанол-вода | Антоин + грубая `f(R) = R/(R+1.5)` | T_head в TAILS получается ~92 °C вместо реальных ~78–82 °C; для проверки логики переходов норм, для оценки качества продукта — нет |
| Захлёб колонны | Косвенный признак: `duty_avg + ΔT_воды` | Не детектирует реальный гидродинамический захлёб (для этого нужен датчик давления в кубе и физическая модель потери напора) |
| Тепловые потери | Линейная 25 Вт/К к окружающей 22 °C | Реальные потери зависят от изоляции, ветра, и т. д. |
| Инерция датчиков DS18B20 | Мгновенные | Реальные DS18B20 в гильзе с термопастой имеют τ ~5–15 сек |
| Сеть Wi-Fi и aioesphomeapi | Pi и ESP в одном процессе | watchdog-тест имитирует разрыв `pi_alive=False`, но не реальные сетевые задержки и retry |
| Перемешивание в кубе | Идеальное | Реальный куб имеет градиент T по высоте, особенно с насадкой |

Если в реальной сессии что-то ведёт себя сильно не так как в симуляторе — это вход в спецификацию, какой компонент модели улучшать.

## Багфиксы и доработки после первой версии

Исправлено после ресёрча на homedistiller.ru/HelloDistiller треды + ESPHome best practices:

- `request_stop()` использовал `time.time()` вместо `t_sim` — заменено на sim-time
- Гистерезис `t_head_over_at` через `hasattr/delattr` → явное поле `Optional[float]`
- `Recipe.t_heat_up_max_s` и `t_body_max_s` — защита от «застревания» в фазе (форум: типовой баг автоматик)
- STABILIZE-выход по совмещению timeout + `|dT_head/dt| < ε` (форум: stabilization is dynamic, not just timer)
- POTSTILL в BODY: клапан узла отбора открыт всегда (не ШИМ)
- Антизахлёб warning при `duty_avg > 0.75` И `ΔT_воды > 30 °C`
- PZEM-style detection: эмержи если `|cmd_power − measured_power| > 0.5 kW` дольше 10 сек (для V1, но реализовано уже в sim)
- Alerts ring buffer (200 строк max) — без memory growth
- Шум датчиков ±0.5 °C и дрейф давления как fault toggles
- Acknowledge emergency button → возврат в IDLE
