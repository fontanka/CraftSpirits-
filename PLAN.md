# CraftSpirits — автоматика дистилляции и ректификации

Самодельная замена БКУ-07М на базе ESP32 (firmware) + Raspberry Pi 4 (standalone Python-сервис с веб-UI и touchscreen на щите). Цель — повторить функционал заводской автоматики, убрать её ограничения и оставить место для собственных алгоритмов. Без зависимости от Home Assistant — можно ставить «как готовое устройство».

## 1. Целевые режимы (MVP → V1)

| Режим | MVP | V1 |
|---|---|---|
| Дистилляция (потстил), отсечка по T куба | ✅ | + отсечка по ΔT/dt и по объёму |
| Ректификация старт-стоп с клапаном | ✅ | + автокалибровка пауз стабилизации |
| ШИМ-отбор (пропорциональный) | — | ✅ |
| Управление охлаждением (bang-bang клапан воды) + ШИМ-клапана узла отбора (LM, по жидкости) | ✅ | + автоадаптация duty по T_head |
| Барокоррекция T кипения по BME280 | — | ✅ |
| Аварийная отсечка (soft+hard) | ✅ | ✅ |
| Логирование + графики в HA | ✅ | + экспорт CSV рецепта |

## 2. Архитектура

**Standalone-приложение, без зависимости от Home Assistant.** Brain в виде Python-сервиса на Raspberry Pi 4, ESP32 — «глупая» периферия с safety, локальный 7" touchscreen на щите + доступ с телефона по LAN.

### 2.1 Физическая схема установки (LM, узел отбора по жидкости)

```
                ┌────────────────────┐
                │  ОБРАТНЫЙ          │  ◄── total reflux condenser:
                │  ХОЛОДИЛЬНИК       │     ВЕСЬ пар конденсируется
                │  на полную         │     в жидкость, ничего наверх
                └─────────┬──────────┘     не выпускает
                          │
                          │ конденсат (жидкость) стекает вниз
                          ▼
                ┌────────────────────┐
                │ УЗЕЛ ОТБОРА (БКУ)  │  ◄── модуль от производителя:
                │  карман + клапан   │     карман-ловушка собирает
                │                    │     конденсат, клапан внизу
                │ ◄── эл/магн клапан │     управляет потоком
                │     ШИМ duty cycle │
                └─────────┬──────────┘
                          │
        ┌─────────────────┴─────────────────┐
        │                                   │
        ▼ (клапан ЗАКРЫТ:                   ▼ (клапан ОТКРЫТ:
        │   жидкость переливается           │   жидкость уходит
        │   через край → в колонну          │   через клапан →
        │   как ФЛЕГМА)                     │   в продукт-приёмник)
        │                                   │
   [Колонна с насадкой]              [Продукт-приёмник]
        │                            (опц. доохладитель)
        ▼
   [Куб с ТЭНом]

   ВОДА: один соленоидный клапан (управляемый ESP) →
         обратный холодильник → слив.
         (Доохладитель продукта если есть — отдельная линия или нет охлаждения.)
```

Ключевая особенность — у нас **нет управляемого дефлегматора с регулируемой температурой**. Обратный (полный) холодильник работает «на полную», запирая колонну в total-reflux режиме. **Узел отбора по жидкости** (заводской модуль БКУ) стоит под обратным холодильником и работает как разделитель потока конденсата: клапан закрыт = вся флегма обратно в колонну, клапан открыт = конденсат уходит в отбор. Регулировка ABV — **только через ШИМ электромагнитного клапана узла отбора**. Это классическая LM-схема (Bokakob style), которая снимает с прошивки задачу PID-управления охлаждением (см. 7.4 — почему наивный PID на reflux ломает колонну) и сводит всё к одному пропорционально-временно́му регулятору.

### 2.2 Логическая архитектура

```
   ┌── DS18B20 × 4 (1-Wire): T_kub, T_head, T_water_in, T_water_out
   │
[ESP32-S3]──ESPHome──── Wi-Fi / native API ───┐
   │                                           │
   ├── SSR ТЭНа (slow PWM, период 5 сек)       │
   ├── SSR клапана узла отбора (LM, ШИМ slow)  │
   ├── SSR клапана воды (bang-bang on/off)     │
   ├── Реле enable-контактора                  │
   └── E-stop / биметалл / термопред (GPIO in) │
                                               │
                       ┌───────────────────────┴───────────────┐
                       │  Raspberry Pi 4 (4 GB) + USB-SSD       │
                       │                                        │
                       │  CraftSpirits Controller (Python)      │
                       │  ├── FastAPI + WebSocket               │
                       │  ├── aioesphomeapi → ESP32             │
                       │  ├── state machines (PotStill,         │
                       │  │       RefluxStartStop, ...)         │
                       │  ├── SQLite (сессии, рецепты, события) │
                       │  └── Telegram alerts (опц.)            │
                       │                                        │
                       │  Web UI (Svelte + Chart.js)            │
                       │  http://still.local:8000               │
                       │       ▲                                │
                       │       │                                │
                       │  Chromium kiosk → localhost:8000       │
                       │       │                                │
                       └───────┼────────────────────────────────┘
                               │ HDMI + touch
                       ┌───────┴──────────┐
                       │ 7" Touch Display │  ← на дверце щита
                       └──────────────────┘
```

**Разделение ответственности — критично для безопасности:**

- **ESP32 (ESPHome)** — единственный, кто физически управляет SSR/реле. Знает только примитивы: «выставь мощность ТЭНа N%», «открой клапан». Имеет независимые safety-инварианты, которые отрубают железо при их нарушении даже без команды сверху.
- **Raspberry Pi 4 (CraftSpirits Controller)** — высокоуровневая логика режимов, рецепты, история, UI. Падение Pi не должно приводить к небезопасному состоянию: ESP должен сам уйти в safe state по watchdog (нет команды > 30 сек).
- **Touchscreen** — это просто браузер, открытый на `localhost:8000`. Падение Chromium не влияет на ничего, кроме UI.

**Почему не Home Assistant**: standalone делает систему независимой от HA-обновлений, упрощает развёртывание (один Docker образ или systemd-юнит), позволяет упаковать как готовый продукт. Минус — теряем «бесплатные» интеграции HA (но Telegram и базовый веб-доступ делаем сами).

**Почему именно ESPHome на ESP32** (а не своя прошивка): YAML-конфиг вместо C++, OTA из коробки, отлаженные драйверы DS18B20/BME280/slow-PWM, официальный Python-клиент `aioesphomeapi` для разговора с Pi.

### Стратегия «без пайки»

Заменяем пайку на три механизма:
- **Винтовые клеммы** на каждом модуле (выбираем модули с встроенными)
- **Wago 221** — рычажные клеммники для 230В соединений и распределения шин датчиков
- **НШВИ + кримпер** — оконцовка многожильного провода в винтовые клеммы (5 сек на провод)
- **DuPont F-F джамперы** — сигнальные соединения между модулями и ESP

Единственный возможный риск: если попадётся BME280 без впаянных штырей. В BOM явно указано «assembled» — проверяйте перед заказом.

**Принцип hardware safety:** ТЭН питается через цепочку `автомат → УЗО → E-stop (NC) → биметалл куба (NC) → термопредохранитель (NC) → катушка контактора → SSR → ТЭН`. Любой разрыв в цепи NC = ТЭН обесточен, и софт тут не участвует.

## 4. Распиновка ESP32-S3-DevKitC-1

Избегаем: strapping pins (GPIO 0, 3, 45, 46), USB-OTG (19, 20), UART0 to USB-serial (43, 44), reserved для octal PSRAM (33–37 на варианте N16R8). Все выбранные GPIO безопасны на любой вариации DevKitC-1.

| Функция | GPIO | Тип | Примечание |
|---|---|---|---|
| SSR ТЭНа (slow PWM) | 6 | output (LEDC) | Период 2–5 сек, 0–100% мощность по полупериодам |
| SSR клапана узла отбора (LM) | 7 | output | High = клапан в узле отбора открыт, конденсат уходит в продукт. Прямое 3.3В на вход Omron G3MB. ШИМ-управление в фазах HEADS/BODY/TAILS, период 30–120 сек. |

## 5. Силовая схема и расчёты

Всё для самостоятельной сборки силового узла + цифры для проверки. Под однофазную сеть 230 В AC, ТЭН резистивный, нагрузка до 5 кВт.

### 5.1 Полная топология

```
[Дом, главный щит]
     │
   УЗО 30 мА AC, ≥25 А
     │
   Автомат C25 (под 5 кВт) или C16 (под ≤3 кВт)
     │
     │  ВВГнг 3×4 (или 3×2.5)
     ▼
┌─────────────────── НАШ ЩИТ (DIN, IP54) ──────────────────────────┐
│                                                                   │
│   L ───┬─────────────────────────────────────────────────         │
│        │                                                          │
│        ├──► Mean Well IRM-15-5 (230AC → 5V DC, для ESP+реле)      │
│        │                                                          │
│        ├──► БП Raspberry Pi 4 (отдельный 5V 3A USB-C PSU)         │
│        │                                                          │
│        │   ┌──── SAFETY CHAIN ──── катушка контактора ────┐       │
│        │   │                                              │       │
│        ├───┤ E-stop NC → KSD9700 NC → KSD9700 NC →       │       │
│        │   │ термопред NC → ESP-enable relay NO →        │       │
│        │   │ катушка KM (~5W, 230VAC)                    │──┐    │
│        │   └──────────────────────────────────────────────┘  │    │
│        │                                                     │    │
│   N ───┤                                                     │    │
│        │                                                     │    │
│   ╔════╪═════════════════════════════════════════════════════╪══╗ │
│   ║  СИЛОВОЙ КОНТАКТОР KM (2NO 25A, катушка 230VAC) ─ замок ║ │
│   ║                                                          ║ │
│   ║  L1 (после KM) ──► предохр 25A ─► SSR Fotek-80DA ─► ТЭН ║ │
│   ║                                          │              ║ │
│   ║                                          └─ R-C снаббер ║ │
│   ║                                                          ║ │
│   ║  L2 (после KM) ──► Omron G3MB ─► соленоид воды 230V     ║ │
│   ╚══════════════════════════════════════════════════════════╝ │
│                                                                   │
│   L (до KM, всегда живая) ──► Omron G3MB ─► клапан БКУ           │
│           (отбор не зависит от контактора — но E-stop его         │
│            всё равно снимет через ESP по watchdog)                │
│                                                                   │
│   PE ──┬─► корпус щита                                            │
│        ├─► корпус ТЭНа                                            │

```

**Ключевая идея**: силовой контактор — это «общий замок». Когда он отжат, ТЭН и клапан воды физически обесточены, даже если SSR залип в проводящем состоянии. Контактор отжимается:
- Любым размкнутым NC-контактом в safety chain (E-stop, биметалл, термопред)
- Размыканием ESP-enable relay (программная команда от Pi или watchdog ESP)
- Пропаданием 230В в сети (катушка обесточена)

### 5.2 Safety chain — детально

Серийная цепь из NC-контактов аварийников + NO-контакт ESP-enable relay, замыкающая катушку силового контактора:

```
       Линия L (230VAC)
              │
        ┌─────┴─────┐
        │  E-stop   │  ◄── грибок 22мм, NC, фиксируемый
        │   NC      │     (нажат → разрыв)
        └─────┬─────┘
              │
        ┌─────┴──────┐
        │ Биметалл#1 │  ◄── KSD9700 110°C, NC,
        │  на кубе   │     на корпусе куба через термопасту
        │   NC       │     (T > 110°C → разрыв)
        └─────┬──────┘
              │
        ┌─────┴──────┐
        │ Биметалл#2 │  ◄── второй на корпусе SSR-радиатора
        │ на радиат. │     (если перегрев SSR > 110°C → разрыв)
        │   NC       │
        └─────┬──────┘
              │
        ┌─────┴──────┐
        │ Термопред  │  ◄── керамический, 130–140°C, NC, одноразовый
        │   NC       │     рядом с биметаллом #1, «последний рубеж»
        └─────┬──────┘
              │
        ┌─────┴─────┐
        │  ESP-     │  ◄── релейный модуль 1ch, катушка от GPIO 12
        │  enable   │     NO-контакт: замыкается когда ESP активирует
        │  relay NO │     (нет питания / ESP в reset → разомкнут → KM отпал)
        └─────┬─────┘
              │
        ┌─────┴─────┐
        │ Катушка   │  ◄── ABB ESB25-40N-06 / Schneider iCT25 / IEK
        │ контакт.  │     230VAC, ~5W, втягивание ~150мА, удержание ~25мА
        │  KM       │
        └─────┬─────┘
              │
       Нейтраль N
```

**Почему именно так:**
- Все аварийники — **NC** (normally closed): «нет питания на катушке = разомкнуто». Любой обрыв провода или поломка датчика = безопасное состояние. (Если сделать NO — обрыв провода имитирует «всё в норме».)
- ESP-enable relay — **NO** (normally open): «нет питания ESP = разомкнуто». При reset/потере питания/прошивке/любом сбое ESP — катушка обесточена, KM отпадает. Программная команда «всё в норме» = удерживать включённым.
- Контакты NC-аварийников должны выдержать ≥0.5 А, 250 В AC. Стандартные грибок и KSD9700 справляются без проблем (катушка KM тянет всего 0.025–0.15 А).

### 5.3 Расчёты для 3 кВт и 5 кВт

#### Токи и сечения проводов

| Цепь | Мощность | Ток (230 В) | Сечение | Допустимо |
|---|---|---|---|---|
| ТЭН 5 кВт | 5000 Вт | **21.7 А** | ВВГнг 3×4 (Cu) | 32 А в трубе, 38 А открыто |
| ТЭН 3 кВт | 3000 Вт | 13.0 А | ВВГнг 3×2.5 (Cu) | 25 А в трубе |
| Соленоид воды | ~10 Вт | 0.04 А | ПВС 2×0.75 | 6 А |
| Клапан БКУ | ~20 Вт | 0.09 А | ПВС 2×0.75 | 6 А |
| Катушка KM | ~5 Вт | 0.022 А | ПВС 2×0.5 | 3 А |
| БП логики 5В (первичная) | ~15 Вт | 0.07 А | ПВС 2×0.5 | 3 А |
| Pi 4 + дисплей (USB-C) | ~15 Вт | 0.07 А | стандартный USB-C | — |

**Везде кратный запас.** Алюминий не использовать ни в каких силовых цепях этого проекта.

#### Падение напряжения на проводке ТЭНа

ВВГнг 3×4 Cu имеет погонное сопротивление **R ≈ 4.61 мОм/м** на одну жилу. При длине трассы 10 м (туда+обратно = 20 м):

```
V_drop = I × 2L × R/L = 21.7 × 20 × 4.61e-3 = 2.0 В = 0.87 % от 230 В
```

Приемлемо. Если трасса >25 м — пересчитайте; на 30 м это уже 2.5–3 %, что снижает мощность ТЭНа на ~5 %.

#### Тепловыделение SSR + размер радиатора

SSR (тиристорная пара, типичные данные с datasheet Crydom D2425 / Fotek SSR-80DA): падение напряжения при полной проводимости **V_on ≈ 1.5 В**.

```
P_diss = V_on × I
3 кВт:  P_diss = 1.5 × 13.0 = 19.5 Вт
5 кВт:  P_diss = 1.5 × 21.7 = 32.5 Вт
```

Допустимая температура корпуса SSR: до 80 °C (выше — резкое снижение допустимого тока, риск отказа). В щите летом окружающая 35–45 °C ⇒ допустимое превышение:

```
ΔT_max = 80 - 45 = 35 °C
R_th_required = ΔT_max / P_diss
```

| Мощность | P_diss | R_th нужно | Что взять |
|---|---|---|---|
| 3 кВт | 19.5 Вт | ≤ 1.79 K/W | Радиатор 120×80×30 мм (≈1.5 K/W) ✅ |
| 5 кВт | 32.5 Вт | ≤ **1.08 K/W** | Радиатор 150×100×40 мм (≈0.9 K/W) ✅ ИЛИ 100×60×30 мм + вентилятор 40×40 12В |

**Важный вывод**: радиатор 100×60×30 мм без вентилятора при 5 кВт перегреется. Варианты:
1. Купить радиатор покрупнее (рекомендуется): «алюминиевый радиатор 150×100×40 для SSR» на AliExpress ~$10
2. Поставить вентилятор: тихий 40 мм 12В с регулировкой по T (через термостат KSD9700 75°C NO)
3. Ограничить мощность до 4 кВт (тогда 100×60×30 справится)

После сборки **обязательно тест в Phase 3** (см. секцию 12, Тест 5): 30 минут полной нагрузки, замер температуры SSR ИК-термометром или контактным.

#### Снаббер RC — когда нужен

| Сценарий | Снаббер? | Почему |
|---|---|---|
| SSR-80 + ТЭН (резистивная) | **Опционально, рекомендую** | Гасит EMI при коммутации, снижает помехи на 1-Wire и WiFi. R=100 Ω 2 Вт + C=0.1 мкФ X2 250 В AC параллельно ТЭНу, провода как можно короче |
| Omron G3MB + соленоид воды | **Не нужен** | В G3MB-202P встроен MOV и snubber для индуктивных нагрузок |
| Omron G3MB + клапан БКУ | **Не нужен** | Аналогично |
| Реле + катушка контактора | **Желательно** | MOV (варистор) 275 В прямо параллельно катушке контактора — гасит ЭДС самоиндукции при отпускании |

Снаббер для ТЭНа собирается из двух выводных компонентов: плёночный конденсатор 0.1 мкФ X2 + резистор 100 Ом 2 Вт **в последовательной** цепи, всё параллельно ТЭНу. Можно сделать прямо на клеммной колодке через НШВИ. Или купить готовый модуль `RC snubber 0.1uF 100R AC` на AliExpress (~$3).

### 5.4 Контактор — почему модульный и какой

Нужен модульный AC-контактор (на DIN-рейку, тихий — без «щелчков» при включении). Требования:
- **Катушка 230 В AC** (не 24 В DC! Внимательно при заказе)
- **2 NO силовых контакта** (один для ТЭНа, второй для соленоида воды) или 1 NO ≥25 А (соленоид можно через тот же контакт)
- **Ток** ≥25 А для 5 кВт (с запасом), ≥16 А для 3 кВт
- **AC-1 категория** минимум (резистивная нагрузка), AC-3 не нужно

Конкретные модели:
- **ABB ESB25-40N-06** — 25 А, 4NO, катушка 230VAC. Самый «правильный», ~$25
- **Schneider iCT25** — 25 А, 2NO, катушка 230VAC. ~$20
- **IEK КМИ-22510** или **КМ-25** — бюджет, ~$10. Работают, но щёлкают громче

Контактор имеет вспомогательный NO-контакт у некоторых моделей (1NC+1NO) — пригодится для индикации в ESP («контактор реально включился»), но не обязательно.

### 5.5 Заземление PE

Без компромиссов:
- PE-шина в щите → отдельная медная шинка с винтами, не объединять с N
- PE → корпус щита (если металлический)
- PE → **корпус куба** (через болт-«земля» на дне или сбоку)
- PE → корпус БКУ / дефлегматора (если металл)
- PE → корпус Pi 4 (если корпус металлический, например Argon NEO)
- Сечение PE-провода = сечению фазы (4 мм² при 5 кВт)

Проверка после монтажа: мультиметром R < 1 Ом между корпусом ТЭНа и PE-шиной щита. Затем УЗО-тестером (или просто кнопкой TEST на самом УЗО) — должно отрабатывать.

### 5.6 Порядок включения и отключения

Чтобы не «дёргать» SSR:
1. Включение: сначала Pi (boot ~1 мин) → потом ESP подключается к Wi-Fi → отзывается на Pi → Pi даёт команду `enable_contactor` → ESP замыкает enable-relay → KM втягивается → 230 В на SSR → SSR ждёт команду PWM
2. Выключение нормальное: Pi даёт `heater=0, valves=closed, enable=off` → ESP размыкает enable-relay → KM отпускает → пропадает 230 В на ТЭН и клапан воды
3. Аварийное (E-stop, биметалл, термопред, watchdog): KM отпадает мгновенно (≤20 мс = один цикл AC), независимо от состояния SSR. Pi+ESP узнают по входу состояния и записывают событие в БД

## 6. Программный стек

Standalone, два уровня: **ESPHome на ESP32** (firmware) + **CraftSpirits Controller на Pi 4** (Python-сервис с веб-UI).

### 6.1 ESPHome-прошивка (`firmware/esp32-still.yaml`)

Делает только то, что обязано — никакой высокоуровневой логики:

- читает все датчики (DS18B20 + BME280) с периодом 1 с;
- публикует sensor entities через **ESPHome native API** (Pi слушает через `aioesphomeapi`);
- принимает команды: `set_heater_power` (0–100%), `valve_takeoff` (клапан узла отбора LM, on/off с управлением ШИМа из Pi), `valve_water` (вода on/off), `enable_contactor` (on/off), `beep` (ms);
- ШИМ ТЭНа через **slow PWM** на GPIO → SSR, период 2–5 сек (для термической инерции это правильнее, чем фазовая регулировка);
- **safety automations** (выполняются на самом ESP, **без Pi**):
  - watchdog: если нет валидной команды от Pi > 30 с → heater=0, valve_takeoff=closed, valve_water=open (продолжаем охлаждение пока колонна остывает), через 5 мин valve_water=closed, contactor=off, beep;
  - T куба > `max_kub_temp` (по умолчанию 105°C) → heater=0;
  - T любого критичного датчика == NaN или вне диапазона `(-10, 130)` дольше 5 с → heater=0;
  - E-stop input == low → heater=0, valve=closed, contactor=off;
  - при загрузке: всё в safe state, контактор включается только по явной команде Pi.

## 7. Алгоритмы режимов

### 7.1 Дистилляция (потстил)

```
INIT → HEAT_UP → DISTILLING → SHUTDOWN
```

- `HEAT_UP`: heater=100%, ждём T_kub ≥ `t_start` (по умолч. 80°C).
- `DISTILLING`: heater=`p_work` (60-80%), клапан всегда открыт. Логируем.
- Переход в `SHUTDOWN`: T_kub ≥ `t_stop` (98-99°C, с барокоррекцией) ИЛИ dT_kub/dt > порога (вода пошла).
- `SHUTDOWN`: heater=0, beep, журнал.

### 7.2 Ректификация со старт-стоп клапаном узла отбора (LM)

```
INIT → HEAT_UP → STABILIZE → HEADS → STABILIZE2 → BODY → TAILS → SHUTDOWN
                                       ↑__ШИМ открытия клапана узла отбора__↓
```

Контролируемая величина — **доля времени открытия клапана узла отбора** (duty cycle), не клапана охлаждения. Период ШИМ 30–120 сек (длинный, чтобы успевала восстановиться флегма после каждого открытия).

- `HEAT_UP`: heater=100%, клапан узла отбора ЗАКРЫТ (вся флегма обратно в колонну, нагреваем до выхода на режим). До `T_head > 78°C` стабильно ≥3 мин.
- `STABILIZE`: heater=`p_work`, клапан узла отбора ЗАКРЫТ → **total reflux mode**. Ждём `t_stable` (10–15 мин) с условием `|dT_head/dt| < ε` — колонна «успокоилась», концентрационные градиенты установились.
- `HEADS`: ШИМ клапана узла отбора с **низким duty** (10–20 %, типично `open 3–10 сек / close 30–60 сек`). **Выход — primary**: датчик уровня в приёмнике голов сработал (сифон автопереход на следующий приёмник = головы кончились). **Backup**: `T_kub > t_kub_body` или фиксированное время. При сбое датчика уровня (контакты окислились → молчит) → backup триггерит и логируется warning.
- `STABILIZE2`: между HEADS и BODY — снова закрыть клапан на 5–10 мин, дать колонне восстановить флегму после интенсивного снятия голов.
- `BODY`: ШИМ клапана узла отбора с **рабочим duty** (30–50 %). Основной отбор. Выход: `T_head > t_head_max` (~78.5°C + барокоррекция) дольше `t_dwell` ИЛИ `T_kub > t_kub_tails`.
- `TAILS`: высокий duty (50–80 %) или вообще открыт постоянно, до `T_kub > t_kub_stop`. Хвосты собираются в отдельную ёмкость (опц. второй клапан-делитель).
- `SHUTDOWN`: heater=0, клапан узла отбора closed, клапан воды closed (через 60 сек, чтобы холодильники остыли).

Все пороги — поля в JSON-рецепте в БД, редактируются из UI, версионируются (каждое изменение — новая ревизия рецепта). **При смене фазы — explicit reset ШИМ-параметров** (см. пункт 10 секции 12.3).

### 7.3 ШИМ-отбор — параметры и адаптация

Для LM-схемы с узлом отбора это **главный и единственный** регулятор разделения. Алгоритм:

```
period = 60 сек (типично, 30–120 параметризуется)
duty = duty_for_current_phase  # 10% heads, 40% body, 70% tails
t_open = period * duty
t_close = period - t_open

while in_phase:
    open_steam_valve(); sleep(t_open)
    close_steam_valve(); sleep(t_close)
    if barocorr(T_head) > t_head_max for > t_dwell: break
```

**Адаптация duty (V1)**: каждые N циклов смотрим `dT_head` за период. Если T_head растёт быстрее `r_max` °C/мин — снижаем duty на ΔD. Если стоит на месте при допустимой T — повышаем. Это даёт «мягкий» PID на основе наблюдения, без скрытых ловушек.

**Не делать**: пытаться напрямую PID `(T_head → duty)` с большим коэффициентом — короткий период регулирования + большая инерция колонны (≥3 мин) дадут осцилляции.

### 7.4 Управление охлаждением — bang-bang (без PID)

У нас **нет управляемого дефлегматора** (partial condenser с регулируемой температурой). Сверху колонны стоит **обратный холодильник** на полную мощность — он всегда полностью конденсирует ВЕСЬ пар в жидкость, которая затем попадает в узел отбора. Поэтому регулировать охлаждение нечего:

- Клапан воды: **bang-bang**. Открыт всю сессию (HEAT_UP … TAILS), закрыт на SHUTDOWN/E-stop через 60 сек после snятия мощности (даём холодильникам остыть).
- Расход воды на входе — постоянный, выставляется ВРУЧНУЮ краном-смесителем под условие: `T_water_out < 50°C` на максимальной мощности.

**Почему НЕ PID** — отдельно объяснено в секции 12.10 («Bang-bang vs PID для reflux column»). Кратко: наивный PID(T_vapor → water_flow) на total reflux condenser попадает в subcool trap (PID гонит охлаждение на 100 %, колонна запирается, T_vapor больше не меняется, PID слепнет). Если бы у нас был partial condenser/дефлегматор с разделением фракций по теплоте конденсации — cascade PID имел бы смысл. У нас этого нет, и не надо.

**Tripwire-логика (соседство с safety)**:
- `T_water_out > 50°C` стабильно >30 сек → warning в UI («поток воды упал?»)
- `T_water_out > 65°C` → автоматическое снижение heater на 50 %
- `T_water_out > 80°C` → emergency shutdown (контактор отжат)

PID **остаётся** только для одного места: slow PWM ТЭНа (целевая мощность → выдаваемая через slow-PWM SSR). Это простой одноконтурный регулятор без подвохов.

## 12. Подводные камни (свод из forum.homedistiller.ru)

Систематизация типичных проблем из веток форума по автоматике, которые наша архитектура должна покрыть (или явно проигнорировать с обоснованием). Источники — внизу секции.

### 12.1 Силовая и SSR

1. **Пробой тиристорной пары SSR в проводящее состояние** — самая страшная авария. Симптом: SSR залип «на нагрев», PWM игнорируется, ТЭН греет на 100 %, никакая прошивка не спасает. На форуме это упоминается как причина серьёзных инцидентов; авторы Samovar и HelloDistiller специально защищаются от этого.
   - **Наш ответ**: силовой контактор как «общий замок» (см. секцию 5.1). Контактор отжимается по watchdog/E-stop/биметаллу — независимо от SSR.
   - **TODO для V1**: контроль реальной мощности через PZEM-004T и отжим контактора при расхождении заданной vs измеренной >10 % в течение 10 сек (как сделал Samovar).

2. **Перегрев SSR при 5 кВт на маленьком радиаторе** — 32.5 Вт тепла, радиатор 100×60×30 не справляется. Выгорает SSR за часы.
   - **Наш ответ**: радиатор 150×100×40 (5 кВт) или 120×80×30 (3 кВт), обязательный Тест 5 в Phase 3.

3. **Помехи от тиристорной коммутации мешают всему**: WiFi отваливается, DS18B20 даёт CRC errors, OLED-дисплеи дохнут после нескольких сессий, индукционные плиты создают токовые скачки.
   - **Наш ответ**: ферритовое кольцо на проводе 1-Wire (как минимум — на кабеле к выносному датчику), снаббер RC параллельно ТЭНу, экранированная витая пара cat5e+экран для длинных трасс, питание ESP и Pi от изолированных БП (Mean Well IRM + отдельный USB-C PSU). Кабель датчиков НЕ прокладывать параллельно силовому проводу — пересекать под 90°.

### 12.2 DS18B20

4. **Длина кабеля >30 м → искажение фронтов → CRC errors**. У нас все трассы ≤3 м — не критично, но если потянем выносной датчик (например, в шкаф для дрожжей) — учесть.
   - **Наш ответ**: ESPHome автоматически делает retry при CRC ошибке, фильтрация в `dallas` компоненте уже включена. Если потащим длинный кабель — экранированная витая пара + ферритовое кольцо.

5. **Параллельное питание ТЭНа и шины 1-Wire на одной фазе** → провалы напряжения 5В → датчики кратковременно «зануляют» соседа по шине. Один пользователь на форуме рекомендует **электролит 50 мкФ на 5В прямо у первого датчика на шине** — решает проблему.
   - **Наш ответ**: добавить керамику 100 нФ + электролит 47–100 мкФ на первой клемме 1-Wire в щите. Дёшево, эффективно.

6. **DS18B20 умирают без предупреждения** (полностью замолкают на 1-Wire). Часто после нескольких лет, иногда блокируют всю шину.
   - **Наш ответ**: алгоритм safety должен переносить потерю любого ОДНОГО датчика без катастрофы. Различение critical/non-critical:
     - **Critical** (потеря = немедленный safe shutdown): T_kub
     - **Important** (потеря = понижение мощности до 50 % + warning): T_head
     - **Nice-to-have** (потеря = warning в UI, продолжаем): T_cond_in, T_cond_out

7. **Заземление экрана с одной стороны** (на стороне БП, не на стороне ESP) — иначе «земляная петля» сама ловит помехи.

### 12.3 Алгоритмика отбора

8. **Чёткие температурные границы для голов/сердца/хвостов невозможны** — зависят от куба, материала, крепости браги, давления. Что работает в один день — не работает в другой.
   - **Наш ответ**: параметры (T_start, T_stop, ШИМ-паузы) задаются на старте сессии, и должна быть лёгкая возможность подкрутить «на лету» из UI. Не зашивать в код. Сохранять фактические параметры успешной сессии как «пресет».

9. **Барокоррекция критична на длинных сессиях**: за 8–9 часов перегонки погода меняется, T_кипения этанола дрейфует на ±0.5 °C при ΔP ±13 hPa. Без коррекции — ложные срабатывания «конец тела».
   - **Наш ответ**: BME280 + поправка `T_corr = T_meas - k×(P_now - 1013)`, k ≈ 0.037 °C/hPa для этанола. Применять к T_head перед сравнением с порогом.

10. **Опасный паттерн ШИМ-отбора**: пользователи увеличивают паузы до 60–120 сек для лучшей сепарации голов («микро-стабилизация колонны»). Это работает, но если режим сменился (heads → body → tails) а параметры ШИМ не пересбросились — пропуски тела или захлёб.
    - **Наш ответ**: ШИМ-параметры жёстко привязаны к фазе (heads/body/tails), не общие. При смене фазы — explicit reset, явное логирование в БД.

11. **«Залипание» в фазе тела при стабильной T** часами: алгоритм ждёт превышения T_stop, а оно не приходит, потому что мощность недостаточна или мы уже на хвостах но T_head ещё не дошла.
    - **Наш ответ**: timeout на фазу. Если в body >N часов и dT/dt < 0.05 °C/час — алерт оператору в Telegram (не auto-stop). N задаётся в пресете, по умолчанию 6 часов.

12. **Стабилизация перед отбором тела (10–15 мин)** — обязательный шаг, который часто пропускают: после захлопывания клапана нужно дать колонне «успокоиться» с полным флегмированием.
    - **Наш ответ**: в state machine RefluxStartStop явная фаза `STABILIZE` после `HEADS`, перед `BODY`. Длительность параметризуется, default 15 мин.

### 12.4 Клапаны

13. **Соленоидный клапан старт-стопа дребезжит и гудит** при питании <12 В или с тонкой прокладкой. Со временем механика разбивается.
    - **Наш ответ**: клапан БКУ на 230 В AC (как у штатного БКУ-07М), не 12 В DC. Кикдаун катушки гасится встроенным в G3MB-202P MOV.
    - **Совет с форума**: заменить штатные прокладки на силиконовые — клапан тише и долговечнее. Для нашего MVP не делаем, но запомним.

14. **Клапан в зоне горячего этанола** — для LM-схемы клапан в узле отбора работает с конденсатом ~75–80°C (горячий этанол + вода). Латунный соленоид для воды НЕ подойдёт — уплотнения деградируют от спирта.
    - **Наш ответ**: используем **заводской узел отбора БКУ** с уже встроенным спиртостойким клапаном (нерж + FKM/Viton). Электроника только подаёт 230 В на катушку через G3MB SSR. Если катушка 12 В DC — соответствующий драйвер/MOSFET вместо G3MB.

15. **Регулировка отбора через дроссельное отверстие**: на форуме отмечают, что фактический отбор больше расчётного, нужна калибровка диаметра отверстия эмпирически.
    - **Наш ответ**: добавить в первую сессию замер реального отбора (мерным цилиндром за известное время), записать `mL/min при 100% duty` в калибровочную таблицу пресета.

### 12.5 Размещение датчика T_head

16. **Гильза с кривым тепловым контактом меряет температуру стенки, а не пара** — даёт заниженные показания на 0.5–2 °C, особенно если стенка холодная.
    - **Наш ответ**: гильза тонкостенная (≤0.5 мм), полностью погружена в пар (без касания стенки), **заполнена термопастой**, датчик утоплен до дна гильзы. Длина гильзы ≥ 3× диаметр датчика.

17. **Установка термометра не в той точке колонны** — классическая ошибка новичков. T в нижней части колонны не соответствует составу отбора.
    - **Наш ответ**: T_head = **в паровой зоне между верхом колонны и обратным холодильником** (т.е. до конденсации, в самой горячей точке). T_kub = в стенке куба под уровнем жидкости. Два датчика, не один универсальный. Не подменять физически потом — это нарушит алгоритм.

### 12.6 WiFi / связь

18. **WiFi в ESP отваливается раз в N часов** при работе под нагрузкой — частая жалоба на форуме. ESP делает self-reset, но процесс продолжается «слепо», если оператор не следит.
    - **Наш ответ** (уже в архитектуре): ESP — автономный, физически управляет SSR. Pi — только высокоуровневая логика. Двусторонний watchdog 30 сек.
    - **Дополнительно**: ESPHome автоматически переподключается с backoff. Поставить точку доступа физически в зоне щита (если основной роутер далеко).

19. **ESP entering boot loop** (упомянуто в ветке про ESP32+PZEM): редкие code paths в UI триггерили перезагрузку, лечилось только power off.
    - **Наш ответ**: вся «толстая» логика в Pi-Python (где удобно дебажить), на ESP только примитивы. ESPHome конфиг минимально сложный, без custom C++ компонентов в Phase 1–4.

### 12.7 Захлёб и контроль давления

20. **Захлёб колонны** возникает при превышении мощности и/или недостаточном охлаждении. Давление в кубе медленно растёт за 5–15 минут перед захлёбом — это окно для предотвращения.
    - **Наш ответ для MVP**: косвенный признак — `T_water_out` после обратного холодильника растёт (вода не успевает охлаждаться = поток упал ИЛИ парогенерация выше теплоёмкости). Tripwire: `T_water_out > 50°C` warning, `>65°C` снижение мощности, `>80°C` shutdown (см. 7.4).
    - **Наш ответ для V1**: BMP280/BME280 в кубе через тонкую трубку для прямого замера ΔP. **Ограничение**: на форуме отмечают, что измерение давления в малых домашних колоннах <50 мм рт. ст. — на грани шума BMP280 (±1 hPa ≈ 7.5 мм рт. ст.). Реалистично только для больших колонн >2 м.

### 12.8 Эксплуатация и безопасность

21. **Пары спирта невидимы и взрывоопасны** (LEL ~3.3 % об.). Любая искра в зоне пара = пожар.
    - **Наш ответ**: щит автоматики ставим **минимум в 1–1.5 м от куба**, физически разнесён. Все искрящие контакты (катушка KM, реле) внутри корпуса щита IP54. Соленоидный клапан БКУ — заводской с пылевлагозащитой.

22. **Отключение охлаждения = вылет паров в комнату**. Самая частая бытовая авария — закрылся кран или соленоид, нет потока в обратный холодильник.
    - **Наш ответ**: tripwire по T_cond_out: >50 °C → warning + heater_power = 50 %, >65 °C → emergency shutdown + Telegram alert + пищалка. Без расходомера это лучший косвенный способ.

23. **Не отключать установку при разливе/утечке** — искра реле = поджигатель. Цитата из FAQ homedistiller.ru: «не пытайтесь обесточить оборудование на месте аварии при проливе или прорыве паров спирта».
    - **Наш ответ**: E-stop не вырубает щит целиком, а **только цепь катушки контактора** (т.е. снимает 230 В с ТЭНа и клапанов внутри щита, но логика ESP/Pi продолжает работать). Полный обесток установки — только рубильник в **главном щите дома** (вне зоны пара).

24. **Вентиляция помещения** — приток + вытяжка. Без неё пары накапливаются у пола (пары этанола тяжелее воздуха).

#### Подделки Fotek SSR (КРИТИЧНО для пожарной безопасности)

Документировано ProtoSupplies, Hackaday, AussieHomeBrewer, HomeBrewTalk:

- **Поддельные Fotek SSR-25/40/80** массово продаются на AliExpress, eBay, Amazon Marketplace. Внутри корпуса с маркировкой «40 А» стоит реальный триак **BTA16-600 (16 А)** в ранних подделках, **позже урезали до 12 А**. У SSR-80 ситуация может быть ещё хуже.
- **Документированные пожары**: пользователи на homebrewtalk.com описывают, как SSR с лампочкой 100 Вт «адекватно работает», но при подключении ТЭНа 4–5 кВт корпус плавится, идёт дым, а в одном случае «если бы вышли из комнаты — сгорел бы дом». Hackaday в разделе Fail of the Week — несколько драматических разборов.
- **Внутри подделки**: PCB без минимальных зазоров между входной и выходной частью (риск пробоя), реальный триак в 2–3 раза меньше заявленного, термопаста между триаком и корпусом отсутствует или халтурная.
- **Как отличить подделку** (несколько признаков сразу — оригинал, один признак — почти наверняка фейк):
  - **Вес**: оригинальный Fotek SSR-40DA весит ~75 г, поддельный 30–45 г
  - **Шрифт на корпусе**: оригинал — чёткая лазерная гравировка с одинаковой глубиной, подделка — смазанная краска или мелкая печать
  - **Голограмма Fotek** на задней наклейке у оригинала (есть не у всех серий, но если совсем нет — подозрительно)
  - **Цена**: оригинальный Crydom D2440 у Mouser ≈ $25–35, оригинальный Fotek SSR-40DA $10–15 у официальных дилеров. SSR-40DA за $3 с AliExpress = почти гарантированно подделка
- **Наша рекомендация**:
  1. **Лучший вариант**: Crydom D2425 (24 А) или D2440 (40 А) у Mouser/Digi-Key/Farnell — оригинал, гарантия, ~$25–35
  2. **Бюджетный**: SSR-80DA «на нагрузку 22 А» (двойной запас даже от подделки), от поставщика с возвратом, обязательно Тест 5 (тепловой) с замером веса перед монтажом

#### Bang-bang vs PID для reflux column (см. 7.4)

Опыт англоязычных форумов: наивный PID(T_vapor) → reflux_water_flow ломает колонну (subcool trap). Правильный паттерн — **bang-bang клапан воды + ШИМ-отбор**, как реализовано в БКУ-07М и StillDragon-овском «still controller» из коробки. Cascade PID — только для тех, кто хочет «automatic ABV mode» с управляемым partial condenser (дефлегматор с регулировкой охлаждения).

**Для нашей установки эта дилемма даже не возникает**: обратный холодильник работает на полную, частичной конденсации нет. Регулировать охлаждение нечем и незачем — единственный регулятор разделения это ШИМ электромагнитного клапана узла отбора по жидкости (LM, секция 7.3).

#### Архитектура «Pi + микроконтроллер с локальным safety» — проверенный паттерн

BrewPi — самая известная open-source платформа для пивоварения (с 2013 года). Архитектура:
- Arduino держит температурный контроль ферментера локально
- Raspberry Pi — UI, графики, конфиг, история
- Цитата с homebrewtalk.com: «если Pi падает прямо в середине ферментации, Arduino берёт управление, и контроль температуры продолжается»

Это ровно наша архитектура (ESP32 ↔ Pi). Подтверждение, что разделение «brain on Pi, safety on MCU» — рабочий промышленный паттерн для домашних процессов, а не наша выдумка.

#### Larry Athey's rpi-smart-still (github.com/larry-athey/rpi-smart-still)

Близкий по концепции проект (Pi + ESP32, контроль T500 и других колонн с дефлегматором). Уроки:

- Использует **сервоприводы на водяных вентилях** (proportional), не on/off — даёт более тонкий контроль ABV ценой механической сложности и точки отказа (сервопривод)
- Принципиально **требует ручную «training run»** перед автоматизацией: «still must be manually run and notes made». Нет универсального алгоритма, который работает на любом кубе из коробки.
- Явно отказались от ML/AI: «There is no AI in use here» — простая state machine на параметрах из калибровки
- **Не заменяет ручные cuts**: «It's upon the distiller themselves to take cuts because there is no way to make flavor determinations electronically» — наш план MVP с «авто-сердце» по T_head должен иметь явный override через UI

#### Коммерческие системы (iStill, GENIO) — что у них «фишкой»

Для понимания потолка автоматизации:

- **GENIO**: запатентованный алгоритм управления **игольчатым клапаном с шагом 0.0208 мм** даёт constant 96 % ABV выхода. Reflux ratio управляется не водой, а механической задвижкой на парном тракте.
- **iStill**: явное профилирование «recipe» с настройкой heads/hearts/tails cuts; интегрировано управление давлением (active column manager — ACM).
- **Чему учиться**: явное хранение «recipe» (профиля сессии) и сохранение фактических параметров успешной сессии как нового пресета — это та фича, которая делает «домашнюю» автоматику конкурентоспособной. У нас в плане она есть (SQLite пресеты), но стоит уделить внимание UX.

#### Индустриальные стандарты безопасности (TTB / OSHA / NFPA)

Применительно к коммерческим distilleries в США/UK — overkill для дома, но направление правильное:

- **TTB 27 CFR Part 19** — учёт алкоголя, не релевантно
- **OSHA 29 CFR 1910.106** — Flammable Liquids — релевантно: помещение должно быть вентилируемо так, чтобы концентрация паров спирта в воздухе была **<25 % LEL (LEL этанола ≈3.3 % об., значит <0.83 % об.)**
- **NFPA 70 / NEC Class I Division 1 или 2** — электрооборудование в опасной зоне должно быть искробезопасным (Ex-rated). Для дома: щит и реле физически вынести из «горячей зоны» (≥1.5 м от куба), кабели через гермоввод
- **Огнетушитель 40-B:C в радиусе 15 м** от точки операции — минимум для коммерции, дом: углекислотный или порошковый ≥2 кг в той же комнате
- **Газоанализатор на LEL** не обязателен **если** вентиляция достаточная (приток + вытяжка ≥10× объёма помещения в час). У нас на кухне эту цифру не достичь — рекомендуем либо вытяжку, либо опционально дешёвый MQ-3 (этанол) на ESP отдельным каналом GPIO для warning'а; не как safety-critical

#### Проблема «cycle in power input drops vapor out of suspension»

Из StillDragon: если резко включать/выключать ТЭН (а не плавно регулировать), при каждом провале мощности часть пара конденсируется обратно в куб, теряется фракция. Поэтому **slow-PWM с длинным периодом (2–5 сек)** лучше быстрого ШИМа или on/off — нагрев усредняется, поток пара стабилен.

- **Наш ответ**: уже заложено — ESPHome `slow_pwm` с периодом 5 сек.

### 12.11 Глубокий ресёрч второй волны (для калибровки симулятора)

Шесть параллельных исследовательских проходов — русские форумы, английские форумы, гидродинамика колонны, failure modes клапанов, DS18B20/BME280 pitfalls, state-machine best practices. Все находки сразу с привязкой «как смоделировать в sim, чтобы можно было гонять решения».

#### 12.11.1 Гидродинамика колонны и захлёб (количественно)

Формулы и численные диапазоны для нашей насадочной колонны (1.5"/2", SPN или мешка, высота ~1 м):

| Параметр | Формула / источник | Наша колонна (5 кВт) |
|---|---|---|
| Vapor velocity | `v = (Q/ΔH_vap)/(ρ_v·A)` | 1.5" → **3.6 м/с**, 2" → 2.0 м/с |
| F-factor / Cv | `Cv = v / v_flood`; `v_flood` из Sherwood-Eckert | **1.5" → Cv=0.7–0.85 (опасно!)**, 2" → Cv=0.4–0.5 (запас) |
| Δp dry | Ergun `150μv(1-ε)²/dp²ε³` | SPN 1.5": **2–5 мбар/м** |
| Δp wet | Leva `Δp_dry·10^(βL)` | **5–15 мбар/м** в рабочем режиме |
| Δp pre-flood | `Δp_baseline + 30–50%` за 5–15 мин до захлёба | **25–40 мбар/м** = warning |
| HETP @ Cv=0.5–0.7 | Bravo-Fair | **4–7 см** (оптимум) |
| HETP @ Cv<0.3 или near flood | Mackowiak | **10–15 см** (деградация) |
| Hold-up dynamic | Mackowiak | **150–300 мл**, τ_column 3–8 мин |
| Weeping threshold | `v < v_min_wet` | Q < **1.2–1.5 кВт** для 1.5" SPN |
| Flood oscillation | дисперсия T_bottom | ±0.3 °C @ **0.05–0.2 Гц** |
| Foam carryover signature | `dT_head/dt > 0.1 °C/с` + `dABV_head/dt < -0.5 %/с` + Δp spike | детект-окно ~30–90 с |

**Решение под проверку sim**: при 5 кВт 1.5" колонна работает на грани захлёба (Cv 0.7–0.85). Если sim покажет это в реальной сессии — нужен переход на 2".

**Источники для формул**: McCabe-Smith-Harriott Unit Operations гл. 18, 22; Mackowiak *Fluid Dynamics of Packed Columns* (Springer 2010); Billet-Schultes (1999) HETP correlation; Stichlmair-Bravo-Fair (1989) flooding; Sinnott Chemical Engineering Design vol. 6.

#### 12.11.2 Multi-component VLE (не бинарный!)

Критическое открытие с английских форумов (homedistiller.org/wiki/Cuts, треды 79915, 26117): **T_head non-monotonic** при переходе heads → hearts, потому что головы (acetone BP 56 °C, MeOH BP 64.7 °C, acetaldehyde BP 20 °C) лежат **ниже** этанола, а хвосты (1-propanol 97, isoamyl 132, acetic 118) **выше**.

Следствие: ловить «конец голов» по абсолютной T_head ненадёжно. Правильно:
- `d(ABV_takeoff)/dt < threshold` (продукт стабилизируется)
- `d(T_takeoff - T_vapor_column)/dt → 0` (subcool затухает)

Sim должен моделировать **минимум 5 компонентов**: methanol, ethanol, water, 1-propanol, isoamyl. Каждый со своим уравнением Antoine, начальной массовой долей в браге, расчётом equilibrium через `P_total = ΣP_i·x_i`. Это намного сложнее бинарного, но без этого «heads cut detection» проверить нельзя.

#### 12.11.3 Two-node boiler model (puking и dry-out)

Из англо форумов (HD 93650, 76686, 79475): immersion-ТЭН в браге → **верхний слой достигает BP раньше bulk** → film boiling → surging → wash попадает на термоколодец → **ghost readings** (грязный датчик меряет brewery muck, не пар).

Модель куба:
```
[Bulk liquid] ── convective exchange (h↓ с viscosity/solids) ── [Top film]
       │                                                              │
   T_bulk, m_bulk                                              T_film (раньше кипит)
       │                                                              │
   ТЭН погружён в bulk                                  surging → puking events
```

Параметры:
- `viscosity_factor` (1.0 для воды-спирта, 2–4 для зерновой/фруктовой браги, 5+ для густой)
- `solids_fraction` (0 для чистой, 0.05–0.15 для злаков)
- `h_convective` падает с этими двумя
- `puke_probability_per_min` растёт когда `(T_film - T_bulk) > 3°C`
- `probe_fouling`: после puke event — bias на верхнем датчике +N°C на M минут

**Dry-out** из русских форумов:
- `dT_kub/dt > 1 °C/мин` при включённом ТЭНе = индикатор
- `(T_kub_wall - T_kub_liquid) > 10 °C` = сухой ТЭН (если есть оба датчика)
- В момент `V_liquid → 0` теплоёмкость падает скачком → T улетает

#### 12.11.4 Sentinel-значения DS18B20 (магические числа)

Из ресёрча DS18B20 (cpetrich/counterfeit_DS18B20, Tasmota issue 9640, БКУ-099):

| Значение | Что значит | Sim flag |
|---|---|---|
| **-127.0** (raw 0xFC90) | Сенсор молчит / нет CRC / прошивка не записала EEPROM | `disconnected = True` |
| **85.0000** (raw 0x0550) **точно** | Power-on reset OR VDD glitch при convert. **Распознаётся точностью**: валидные 85±0.5 vs ровно 85.0000 | `early_read_p`, `power_glitch_p` |
| **CRC fail** | Проблема шины, EMI, длинный кабель | кластеризуется в 1мс окно вокруг SSR switching events |

Алгоритм для контроллера:
```python
def is_valid_ds18b20(raw_C):
    if raw_C == -127.0: return False  # disconnected
    if raw_C == 85.0000 and abs(raw_C - last_valid) > 5: return False  # power-on
    if abs(raw_C - last_valid) > MAX_DT_DT * dt: return False  # impossible jump
    return True
```

Plus: **счётчики per-sensor** (CRC fail rate, sentinel rate, jump rate). Если один сенсор имеет >5× больше fails чем остальные — это «далёкий» или дохлый.

#### 12.11.5 Counterfeit DS18B20 — 6 семейств

Известных подделок: A1, A2, B1, B2, C, D1 ([cpetrich/counterfeit_DS18B20](https://github.com/cpetrich/counterfeit_DS18B20)):

- ROM pattern fakes: `28-xx-xx-xx-xx-00-00-xx` (середина нулевая)
- **Зависают на 0 °C crossing** (некоторые семейства)
- **Шум σ в 2–10 раз выше** оригинала (детект статистически)
- **Не сохраняют EEPROM** (Tlow/Thigh регистры): тест provision = write + read after power cycle
- Drift 1–2 °C/год (vs 0.1–0.5 для оригинала) + step changes при thermal shock

В sim модель `counterfeit_family` enum с разными параметрами шума, дрейфа, и hang-at-zero-crossing.

#### 12.11.6 Valve state vector (15 переменных на клапан)

Из ресёрча failure modes (Burkert, ASCO, ProtoSupplies, Lee Co, плюс homedistiller форумы):

```python
@dataclass
class ValveState:
    # Динамика
    lift_fraction: float = 0.0  # [0..1] фактическое положение
    open_delay_ms: float = 30   # задержка реакции, растёт с износом
    close_delay_ms: float = 20

    # Износ/возраст
    cycle_count: int = 0
    seal_wear: float = 0.0      # 0..1, износ уплотнения
    insulation_age: float = 0.0 # Arrhenius decay катушки

    # Тепловой режим
    T_coil_C: float = 25
    coil_class: str = "B"       # B=130°C, F=155°C

    # Загрязнение
    seat_debris: bool = False   # частица на седле, leak
    scale_mass_g: float = 0.0   # минеральные отложения (water valve)
    stiction_force_N: float = 0.0  # binding после простоя

    # Проблемы электрики
    V_supply: float = 230.0     # просадка → buzz
    contact_resistance_ohm: float = 0.01  # DIN 43650 коррозия
    snubber_present: bool = True  # без него — kickback damage

    # Параметры flow
    Cv_effective: float = 1.0   # дрейфует ~×1.5 при heat soak (БКУ takeoff)
    leak_rate_ml_s_when_closed: float = 0.0

    # Здоровье общее
    coil_health: float = 1.0    # 0.0 = burned out
```

**Failure modes** (как раскрыты):
1. Dribble — FKM свелл, leak при cmd=closed → растёт ABV в product при паузах
2. Particle bypass — стохастический, P=0.3 self-clear после next cycle
3. Sluggish — `open_delay` растёт со временем
4. Stuck after long-off — calcium на штоке после `>N часов простоя`
5. Coil thermal drop-out — `if T_coil > T_class → coil_health -= dt/τ_aging`
6. Chatter at low V — `if V < 0.85·V_nom → lift_fraction осциллирует @100Гц`
7. Inrush burnout — `if lift < min and t_energized > 2s → coil_dead`
8. Inductive kickback — каждый switching event без snubber: `insulation_damage += spike_energy`
9. Terminal corrosion — Bernoulli `contact_open ~ p(humidity, age)`
10. Water hammer — каждый close event: `seat_wear += ΔP_hammer/E_seat`
11. **БКУ heat soak**: `Cv_effective(t) = Cv_0 · (1 + α·(T_coil - T_ref))` — flow drifts up ×1.5 после 2ч!
12. MTBC: ASCO premium 10M циклов, generic 300k. Weibull k≈2

**Killer insight**: 70-80 % отказов происходят **в момент переключения** (inrush, hammer, kickback). Sim должен катать кости на **каждый edge**, а не раз в N секунд.

#### 12.11.7 Best practices state machine (для нашего кода)

Из обзора (controleng, Astrom-Wittenmark, Memfault, Ganssle):

| Pattern | Что | Проверка |
|---|---|---|
| Bumpless transfer | `u(t+) = u(t-)` на phase transition, back-calculate integral | `\|u(t+) - u(t-)\| < ε` |
| Anti-windup | clamping или back-calculation; HEAT_UP — hotspot | SP далеко от possible → не overshoot после снижения SP |
| Single-writer rule | только один task пишет state; event queue FIFO | fuzz duplicate events → deterministic final |
| Supervisor watchdog | каждый task шлёт heartbeat; кикает HW WD только если все свежие; никогда не из ISR | kill task → HW WD fires |
| Soft + Hard timeouts | per-phase soft alarm + HW reset | HEAT_UP > 45min → soft alarm |
| Safe-state on boot | HW WD reset → safe state, не resume; после EMERGENCY — manual ACK | pull power mid-run → boot в SAFE |
| Monotonic time | `time.monotonic()` Python; `esp_timer_get_time()` ESP32 | NTP jump → no transition |
| Condition vs time transition | условие primary; time только как safety bound | HEADS→BODY по T+ABV stable, time как timeout |
| Operator override hierarchy | Hand > Override > Manual > Auto; tieback для bumpless return | operator sets duty, resume auto → no jump |
| Event log + telemetry | event log append-only durable; telemetry lossy ring | delete state, replay event → identical |

#### 12.11.8 Operator override patterns (когда оператор должен вмешаться)

Из англо форумов (homedistiller.org треды 5518, 54508, 78393, 76686):

| Ситуация | Что замечает оператор | Что делает |
|---|---|---|
| Cooling water inlet T растёт mid-run | distillate plunges below column T | slows water flow до «hot to touch» (это не баг, не паника) |
| Audible «helicopter» whistle | precursor захлёба | cuts power 20–30 %, **не закрывает отбор** |
| Smell/taste — heads-tail edge | sensors не успевают за носом | manual cut |
| Foaming в кубе | observable через окно куба | reduce charge до ~50 %, add Fermcap/oil |

Sim должен экспонировать эти naturals — operator override interface c log того, что оператор делал. Тогда любой rule-based / RL agent сможет учиться на тех же триггерах что человек.

#### 12.11.9 Recipe portability (dimensionless форма)

Из StillDragon /discussion/2019, /discussion/1307, HD 69502, 67253:

**Recipes должны быть dimensionless**, иначе не переносятся между колоннами:
- **Reflux ratio R** (не duty cycle) — `R = L/D` где L=флегма, D=отбор
- **F-factor fraction** = `Cv = v / v_flood` (всегда работаем 0.5–0.7)
- **Energy/kg-charge** (kJ/kg, не kW absolute)

Параметры **column-specific** (хранятся отдельно): D, H, packing HETP curve, wall-loss coefficient, condenser Cv.

Параметры **universal** (VLE, water Cp, ethanol latent heat) — константы кода.

Recipe = `{reflux_ratio_heads: 5.0, reflux_ratio_body: 2.0, Cv_target: 0.6, energy_per_kg: 1200}` вместо `{p_work: 60%, duty_body: 0.4, …}`.

### 12.12 Датчик уровня в приёмнике голов (контактный, БКУ-style)

Заводская сборка БКУ для автоперевода голов состоит из:

- **Сифонное устройство перевода** — чистая механика без электроники. Конденсат из узла отбора капает в приёмник голов, при заполнении (~100–200 мл) срабатывает сифон и поток переключается в следующий приёмник (тельная ёмкость).
- **Контактный датчик уровня** — поплавковый/герконовый, ставится на приёмник голов. При срабатывании сифона = заполнении ёмкости — контакты замыкаются. Это **сигнал «головы кончились»** для нашей автоматики.

Failure modes (из ресёрча первой волны, БКУ-099 thread):

1. **Окисление контактов** от паров спирта (главное!) → пропуск трyger'а ИЛИ дребезг с false trigger'ами. БКУ официально рекомендует **чистить наждачкой перед каждым прогоном**.
2. **Mechanical sticking поплавка** — после длительного простоя или загрязнения. Datchik не сработает даже при полной ёмкости.
3. **Splashes / false trigger** — мокрая обмотка контакта может дать ложное замыкание во время сильного отбора.

Алгоритм в контроллере (см. 7.2):

```python
# HEADS phase
def heads_exit_condition(t_sim, sensors):
    # Primary: level sensor (debounced + sanity check)
    if sensors["level_heads_full"] and _debounce_stable_ms(level_heads_full, 500):
        return ("level_sensor", "primary trigger")

    # Backup: T_kub climbed beyond expected heads endpoint
    if sensors["T_kub"] > recipe.t_kub_body_backup:
        log_warning("level sensor did not trigger, fallback to T_kub")
        return ("t_kub_backup", "backup trigger")

    return None  # stay in HEADS
```

Debounce: контакт считаем «replicating заполнение» только если стабильно замкнут ≥500 мс. Это отсекает кратковременные дребезги от окисления и брызг.

В sim: моделируется `LevelSensor` class с параметрами `oxidation_resistance_ohm` (растёт со временем), `bounce_probability` (вероятность ложного срабатывания на каждый dt), `mechanical_stuck` (boolean — не срабатывает совсем). Тесты должны покрыть: работает нормально / окислился (false trigger) / mechanical stuck (молчит) — во всех случаях алгоритм корректно отрабатывает.

#### 12.13.1 Mash-type-specific алгоритмы (зерновая / сахарная / фруктовая)

Из forum.homedistiller.ru (треды 29928, 102757, 137594, 44512):

| Тип браги | Особенности | Алгоритмические следствия |
|---|---|---|
| **Зерновая** (rye worst) | foam-aggressive, осадок carbonises на ТЭН (burnt aroma), вязкость от крахмала | slow ramp, soft TEN W/cm², longer foam-watch (60–120 sec window после кипения), monitor `dT_kub/dt` для detect нагара |
| **Сахарная** | clean, low-foam, predictable | базовая модель |
| **Фруктовая** (apple/pear/etc) | **pectin → elevated methanol в головах**, pulp settles + burns, cider/wine дрожжи дают много aldehydes | **bigger head cut 8–10 % AA** vs 3–5 % для сахарной; per-type T_kub upper limits |

**Что в sim**:
- Recipe.mash_type ∈ {grain, sugar, fruit, mixed} + density/viscosity profile
- Foam probability ∝ grain_fraction × P_TEN × dT/dt (стохастический burst)
- Pectin → MeOH boost в y_vapor: в `initial_mash_composition` для fruit увеличить x_methanol в 5–10× от base
- «Burnt-on-TEN» state: progressively distorts T_kub vs P_heater slope над сессиями
- Head_cut_volume_target в recipe = f(mash_type, V_kub, initial_ABV)

#### 12.13.2 Multi-pass pipeline (Run1 → Run2)

Стандартная практика: Run1 = быстрый потстил без cuts «до сухого» (≤5 % в струе) → SS разбавляется до 20–15 % ABV перед Run2 (75–80 % fill) → Run2 = ректификация с cuts.

**Что в sim**:
- Session.run_type ∈ {potstill, reflux_first, reflux_second}
- Persisted metadata между прогонами: SS_volume, SS_ABV, SS_congener_load
- Two-mode state machine — Run1 имеет другой exit (T_kub ≈98–99 + stream <5 %), Run2 — ректификация с cuts
- Sim chain test: Run1 → Run2 на тех же физических параметрах, продукт второго прогона должен быть значительно крепче

#### 12.13.3 Парковка голов («oborotniy спирт»)

Из azbukavinokura.com (shag-2-peregon), forum.homedistiller.ru (104237, 104994, 6891):

Heads (3 %) + подголовники (5 %) от прошлого прогона сохраняются и либо добавляются в куб следующей сессии, либо ректифицируются отдельным проходом «оборотного спирта». При парковке в кубе **больше congeners → длиннее head phase**.

**Что в sim**:
- Persistent oborotniy_pool: {V_L, ABV, x_mass (5-component)}
- При старте сессии — если operator выбрал «co-charge oborotniy» → начальный куб получает дополнительный congener load
- Cut detector переключается с `dT_head/dt` на **cumulative-volume gate** + methanol-proxy
- Head cut volume увеличивается пропорционально added congener mass

#### 12.13.4 Gin basket / ароматизация — важный спец-режим

Из forum.homedistiller.ru (287043, 351364, 281487):

Травы/специи в gin basket (или царге пастеризации) **должны активироваться только в фазе BODY**. Если включить во время HEADS — аромат уйдёт с головами безвозвратно. T_head в этом режиме:
- **Слегка выше** (травы создают доп. Δp)
- **Шумнее** (absorb некоторое количество reflux)

**Что в sim**:
- Recipe.gin_basket_enabled: bool
- Если True: дополнительный Δp +50–200 Pa, T_head_target += 0.3–0.8 °C, noise σ × 2
- **Critical**: не триггерить heads-end ТОЛЬКО по T_head — обязательно через level sensor или cumulative volume

#### 12.13.5 Re-fermentation в кубе (CO2 outgassing)

Из forum.homedistiller.ru (57106, 51457):

Подмоложенная брага при медленном нагреве **резюмирует CO2 выделение при 30–50 °C** — до начала кипения. Foam/pressure spikes ПЕРЕД любым vapor. Алгоритм может принять за «начало работы» и поведение ломается.

**Fix**: требовать `T_kub > 70 °C` ПЕРЕД любой интерпретацией пены/давления как «approaching boil».

**Что в sim**: 
- FaultInjection.under_fermented: bool
- Если True: CO2 generation в boiler при 30–50 °C → foam height и pressure rise независимо от etohanol vapor (m_dot_vapor = 0)

#### 12.13.6 End-of-session разделение Run1 vs Run2

| Trigger | Run1 (потстил) | Run2 (ректификация) |
|---|---|---|
| Завершение | T_kub ≈98–99 °C + stream <5 % ABV | T_kub 92–94 °C + T_head creep up |
| Acetic mash («уксус пошёл») | sour vinegar smell (бактериальная брага) | distinct от oily/heavy tail |

#### 12.13.7 Recovery после прерывания — phase-aware policy

| Phase / условия в момент прерывания | Recovery action |
|---|---|
| Pre-stabilisation (HEAT_UP / STABILIZE) | **Full restart** — column gradient lost |
| Stable BODY + gap <60 min + T_kub >70 °C | **Re-stabilise** (15–20 мин total reflux) + extended head-recheck → resume |
| Gap >60 min OR T_kub <60 °C | **Rebuild gradient** = full reset |
| TAILS interrupt | Часто abandon (продукт уже основном собран) |

**Что в sim**:
- Checkpoint в SQLite каждые N сек: {phase, t_in_phase, accumulated_V_heads, V_body, V_tails, congener_load_est}
- On boot: SAFE state forced. Если checkpoint <5 min И сенсоры agree (Δ<3K) → пред-arm с приглашением operator подтвердить. Иначе abort с offer «start new session».
- **Никогда auto-resume hot still без operator подтверждения**

#### 12.13.8 Power quality — RU/EE electrical environment

Найдено критически важно для нашей среды.

**Mains voltage / power supply**:
- RU LV grid: 207–253 V (GOST 32144 ±10 %), evening sag до 195–205 V, microcuts 20–200 ms от утилитарных реклоузеров
- **Online double-conversion UPS 300–600 VA** только для Pi+ESP (не для ТЭНа)
- **Offline UPS не подходит**: 4–10 ms переключение + грязный square wave → Pi4 PSUs crash
- AVR/стабилизатор (Resanta, Shtil ~5–10 kVA) **для всего стенда если voltage swings >±15 %**

**RCD / GFCI**:
- **Type A 30 mA** обязательно — Type AC пропускает DC компоненты от SSR/SMPS, Type B только для VFD
- Автоматику на **отдельный 10 mA RCBO** от 30 mA heater'а
- SSR RC snubber leaks 0.5–2 mA capacitively, sheathed heater absorbs moisture → 3–8 mA leakage → суммарно может превысить порог
- Dry preheat heater при первом включении (low-power) — иначе ложное срабатывание УЗО

**Neutral / PE — критично**:
- В старых квартирах **floating neutral** даёт 380 V across loads
- **Isolate cooling water loop с пластиковой муфтой / диэлектрической вставкой** — иначе водопровод (земля) создаёт парасит-путь к корпусу куба
- Pre-commissioning: socket tester + clamp meter на PE (должно быть ~0 mA) + N-PE voltage с нагрузкой (<2 V healthy, >5 V indicates bad N)

**WiFi 2.4 GHz** — крайне ненадёжно:
- **Лучше Ethernet через W5500 SPI** на ESP32 для stationary rig — eliminates 2.4 GHz class problems entirely
- Если Wi-Fi — survey с Wi-Fi Analyzer, channels 1/6/11, external IPEX antenna **≥20 cm от SSR/contactor**

**Grounding советская проводка**:
- TN-C (no PE) в старых квартирах — UNSAFE для RCD
- Aluminum wiring (АПВ) oxidises и creep'ает на терминалах
- Nuclear option: **изоляционный трансформатор 1:1 5–6 kVA** для всей установки (defeats RCD но contains faults локально)

**Lightning protection**:

#### 12.13.9 Calibration & commissioning procedures

**DS18B20 калибровка**:
- Ice slurry from distillate (без плавающей воды!) + steam point with barometric correction `T_boil = 100 - 0.0366×(1013.25 − P_hPa)`
- 30+ readings averaged, linear offset+gain fit
- **Достижимо ±0.05–0.1 °C** (factory 0.5 °C)
- **Coefficients хранить в Pi SQLite по ROM_ID**, НЕ в DS18B20 EEPROM (TH/TL registers — это alarm thresholds, fragile)
- Repeat: после термошока в гильзе + every 6–12 months

**BME280 калибровка**:
- METAR QNH ближайшего аэропорта <30 km same elevation
- Convert: `P_station = QNH × (1 − 0.0065×h/288.15)^5.255`
- Drift ±1 hPa/year typical. Mount в сухом, вентилируемом месте

**Flow-rate calibration узла отбора**:
- Таблица duty × heat-soak: 10/25/50/75/100 % × {cold, 30 min, 2 h}
- Class-A 100 mL мерный цилиндр + timer
- Fit nonlinear curve per heat-soak bin
- Использовать **valve_body_temp как feedforward** для compensation 1.5× heat-soak drift

**Bimetal Klixon тест**:
- Silicone oil bath + reference thermometer
- Ramp <2 °C/min через rated trip point
- Repeat 3× must agree within ±3 °C
- Annual recalibration

**Термопредохранитель**:
- Cannot retest non-destructively — sacrifice 2 of 10 sample
- Verify open within spec at rated T
- Install rest with traceability (lot, install date)
- Continuity test at install только ohmmeter <10 mA
- **Replace preventively every 2 years** или после over-temp event

**Thermowell установка**:
- **Thermal paste обязательна** (никогда dry); для длинных гильз — **quartz sand + mineral oil** (народный трюк HD.ru)
- Insertion depth ≥10× диаметр well
- Calibrate **whole assembly** (sensor + well + paste) — лаг 5–20 sec
- Log τ (63 % response time) per well_ID

**Smoke testing — beyond lamps**:
- DS18B20 emulator from another MCU для testing alarm boundaries (78/85/95/105 °C)
- Decade resistance box (0.1 %) для PT100/NTC если используется
- E-stop response time с logic analyzer — **target <100 ms**
- Test loss-of-1-Wire (cut wire), bus shorted, 85.0000 sentinel, watchdog reboot, brown-out at 4.5 V, network loss Pi↔ESP

**Calibrations table в БД**:
```sql
CREATE TABLE calibrations (
  timestamp INTEGER, device_id TEXT, ref_value REAL,
  raw_value REAL, offset REAL, slope REAL,
  ambient_T REAL, ambient_P REAL, operator TEXT, notes TEXT
);
```
Plot offset vs time per device — drift visible only после ≥3 calibrations.

#### 12.13.10 Mechanical / enclosure long-term reliability

**Антиконденсация (критично для паровой среды)**:
- **Anti-condensation heater 30–60 W в щит**, ПОСТОЯННО включён (не interlocked с main contactor)
- Поддерживает T внутри щита ~5K выше ambient → ничего не конденсируется
- **Gore-Tex breather в НИЖНЕЙ части щита** (силикагель saturates за недели — не подходит)
- Conformal coating акрил на Pi/ESP (easier rework чем urethane)

**Терминалы — re-torque schedule**:
- Copper creep relaxes torque на 20–40 % в первые месяцы
- **24h, 1 month, then yearly** per IEC 60947-1 Table 4 (M3.5 = 0.8 N·m)
- Wago push-in для control wiring предпочтительнее (spring force tracks creep)
- Ferrules на каждую stranded wire, никогда два провода под один винт
- **Annual thermal-imaging scan под полной нагрузкой** — terminal >10K hotter than neighbors = suspect

**Long-term degradation мониторить**:
- Накипь на охлаждающем змеевике: log T_water_in/out, +3–5 K creep over baseline = fouling. Citric acid 2 Tbsp/L @ 50 °C × 30 min, every 50–100 hours run-time
- Накипь на ТЭНе и thermowell: thermowell lag 30–120 sec после нагара → PID overshoot, foamovers. Citric acid soak каждые ~20 batches; descale thermowell отдельно
- EPDM gaskets: silicone grease ежегодно; daylight test в dark room для leak detection
- NPT соединения weep после 50–200 циклов → заменить критичные на **Tri-Clamp + EPDM** (gasket = consumable)

**Hose clamps — критичный отказ**:
- **Oetiker stepless ear clamps (167-series)** на cooling line — 360 ° spring-loaded
- Worm-gear только 270° + cuts hose под over-torque → blow-off mid-run
- Double-clamp anything carrying hot water
- Always barbs, never smooth

**DS18B20 strain relief (mainstreaming reliability)**:
- **Stranded silicone/PTFE** кабель (никогда solid-core CAT5)
- **Adhesive heat-shrink 25 mm onto cable** + отдельный mechanical clamp от electrical termination
- Strong **2.2 kΩ pull-up only at master end**
- Run length **<10 m**
- Parasitic mode disabled

**IP54 vs heat tradeoff**:
- Закрытый IP54 → SSR + Pi heat trapped → MTBF half per +10K above 40 °C
- **Filter-fan + exhaust louver (Pfannenberg/Hoffman)** maintains IP54 + air exchange
- Internal temp logger, fan thermostat on 35 °C off 30 °C

**EMC compartmentalization в щите**:
- **100 mm spacing**: 230V левая зона / 24V средняя / signal правая
- Cross at 90°
- **Single solid ground plane** — НЕ split (induces ringing!)
- Star ground at PE bar
- Ferrite clamp на каждом sensor cable at cabinet entry
- RC snubber на катушке контактора **И** на heater leads
- Shielded sensor cable grounded **ONE end only at controller**

**SSR + Pi orientation**:
- SSR fins **VERTICAL** (horizontal derate 30 %), SSR mounted **высоко** в щите (горячий воздух идёт вверх)
- Thermal paste re-apply каждые 2–3 года
- Pi4 with heatsink + slow fan, mounted ports down
- Никогда electrolytic caps непосредственно над heat sources

**ESD risk зимой (dry RU/EE air)**:
- **Wrist strap clipped to PE bar** перед открытием щита
- **Series resistors 100 Ω–1 kΩ на каждом GPIO** идущем на header
- **TVS diodes** на long sensor runs
- Humidify workshop >40 % RH в зиму
- Never plug/unplug live USB на Pi

#### 12.13.11 Algorithmic edge cases (must-test в sim)

**Hot-start detection**:
- На ARM: измерять T_kub × 30 sec. Если `T_kub > T_ambient + 15` И `|dT/dt|` мал → propose **warm start**: skip HEAT_UP с reduced ramp, operator confirms

**Mid-session recovery checkpoint policy**: см. 12.14.7

**Recipe versioning**:
- Mutations создают **immutable recipe_revision** linked to parent
- Session логирует ordered list of revisions с timestamps
- **Никаких silent overwrites**

**Concurrent operators**:
- Session-level advisory lock с operator_id
- Non-holders: read-only + «request control» handoff
- Telegram bot — тот же lock

**DB growth strategy**:
- Hot table 90 дней
- Nightly archive в compressed DB
- Weekly `PRAGMA wal_checkpoint(TRUNCATE)` + `VACUUM` во время idle

**Sensor swap (DS18B20 ROM change)**:
- Map logical roles (T_kub, T_head) to ROM via config file
- On missing-ROM → SAFE state + prompt operator для re-bind
- Sanity-check new sensor (reading в plausible band) перед resume

**False-end / stale DONE**:
- 2h inactivity timer → auto-transition DONE → CLOSED (close water valve, summary emitted)

**Noise stacking — per-input filtering**:
- P (давление): 1 Hz LPF
- T (температуры): median + EMA
- dT/dt: smoothed derivative on filtered T (not raw)
- PID derivative term clipped
- ABV computed from filtered T only

**Override hierarchy после E-stop**:
- **E-stop release ВСЕГДА → SAFE**, никогда не возвращает в prior overrides
- Operator должен re-assert manual mode explicitly после release
- Mode hierarchy: Hand > Override > Manual > Auto

**Pre-flight cooling water check**:
- Перед HEAT_UP: pulse heater короткий, verify `ΔT_water_out < 2 K` И flow-switch active
- Если ΔT/dt > threshold во время run → immediate cut heater + alarm

#### 12.13.12 2024–2026 landscape

**Software baseline**:
- **ESPHome ≥2025.10** (major architecture overhaul — memory, security). Pin наш firmware baseline
- **⚠️ Raspbian 12 ломает GPIO 17/27 relay reliability** (larry-athey/rpi-smart-still wiki, May 2025). **Pin к Raspbian 11** ИЛИ переход на Orange Pi / Banana Pi

**Сенсорные альтернативы (опционально для V1+)**:
- **MAX31865 PT100** mature ESPHome support, 2/3/4-wire SPI. Для куба/boiler **>125 °C** и в EMI зоне лучше DS18B20
- **SHT45 Sensirion** (±0.1 °C / ±1 % RH) для cooling water inlet / ambient (НЕ для пара)
- **PZEM-004T v3** актуальный (v1 EOL) — наш выбор подтверждён

**Reference проекты**:
- **ys1797/esp32_hd** + OSHWLab schematic — канонический русский ESP32 rectification firmware, отличный reference схемы
- **larry-athey/rpi-smart-still** — Pi + ESP32, серво на воде, ML отсутствует
- **larry-athey/boilermaker** — ESP32 master/slave boiler power controller (pattern для будущего multi-boiler)
- **vitotai/BrewManiacEsp8266** distilling mode — 4 stages (pre-heat / head / heart / tail) — state-machine паттерн совпадает с нашим

**Valve PWM gotcha** (forum.homedistiller.ru 315674):
- AR-HX-3 12V valves: PWM ~60 % needed to **crack open** — bang-bang valve с малым duty может никогда не открыться
- **Soft-start ramp**: первое открытие после долгого закрытого periodа — короткий импульс 100 % затем держим до target duty

**Dual-PWM pattern**:
- Slow PWM (2–5 s period) для boiler SSR
- Fast PWM (>100 Hz) для precision valve / дефлегматора (у нас не дефлегматор, но идея для будущей точной адаптации duty)

**ML / AI cuts detection**: 
- В production нет public projects (open opportunity)
- В академии: LSTM + wavelet для температурного прогнозирования
- Реалистично: train RNN на reference sessions, использовать для рекомендаций, не для автоматических cuts

**Commercial split**: iStill / GENIO теперь отдельные компании (2024–2025). GENIO ушли в oil-jacketed ODG2 250L/1000L для flavored spirits 50–80 %. Не релевантны для дома.

## 13. Dry-тесты — план

Цель — проверить всю логику системы без алкоголя и без реальной дистилляции. Делаем в собранном щите. Лампа вместо ТЭНа, светодиоды/индикаторы вместо клапанов, кружка с водой для прогрева датчиков. **Всё, что описано ниже, выполняется ДО первого боевого запуска.**

### 13.1 Подмены компонентов

| Боевой компонент | Чем заменить для dry test | Зачем |
|---|---|---|
| ТЭН 3–5 кВт | **Лампа накаливания 60–100 Вт** (Е27 в патроне с проводами и вилкой) | Видимая нагрузка, минимум тока (≤0.5 А), не нужен большой радиатор на SSR. Накал ламы видно глазом ⇒ ШИМ проверяется визуально |
| Соленоид воды 230 В | **Лампа-индикатор 230 В неоновая** (зелёная) или сетевой LED 5 В через адаптер | Видимая индикация открытия/закрытия |
| Клапан отбора БКУ | **Лампа-индикатор 230 В неоновая** (красная) | То же |
| DS18B20 (×4–6) | Сами боевые датчики | Опускаем по одному в чашку с горячей/холодной водой, имитируем рост T |
| Куб с ТЭНом | **Электрочайник + датчик внутри** (изолированно, через крышку) | Чайник плавно греет воду — идеальный имитатор ТЭНа для отладки переходов состояний |
| BME280 | Сам боевой | Просто читаем атмосферу комнаты |

Стоимость доп. железа для dry test: ~$10. Лампа в патроне + 2 неонки + чайник, который и так есть.

### 13.2 Последовательность тестов

#### Тест 1 — Базовые I/O (Phase 1)

1. Прошить ESPHome на ESP32, подключить DS18B20 + BME280.
2. Поднять `controller/` на Pi (или ноуте в режиме разработки), подключиться к ESP через aioesphomeapi.
3. В веб-UI на `http://still.local:8000/tests` (экран «Tests») убедиться: все датчики читаются, значения обновляются раз в 1–5 сек.
4. Поднести зажигалку к гильзе DS18B20 (НЕ на пластик!) на 5 сек — T должна вырасти на 10–20 °C, потом упасть.
5. Подышать на BME280 — влажность подскочит на 10–20 %.

**Прохождение**: все 4 датчика T и BME280 видны в UI, реагируют на тепло.

#### Тест 2 — Логические выходы (Phase 2)

1. Собрать щит до уровня «ESP + screw shield + SSR + реле», но **без подключения к 230 В сети**.
2. На вход 230 В подать через лампу-индикатор 60 Вт (т.е. в разрыв линии), чтобы видеть «есть/нет напряжение на нагрузке».
3. Из UI экрана «Tests» нажать `[TEST 5s]` на каждом выходе → соответствующая лампа-индикатор должна загораться на 5 сек.
4. Для ТЭН-выхода: задать ШИМ 50 % на 30 сек → лампа на выходе SSR должна **мигать** с периодом 2–5 сек, ~равные интервалы on/off.
5. Проверить кнопку BEEP → пищит.

**Прохождение**: каждый выход срабатывает по команде, ШИМ виден как чёткое мигание лампы.

#### Тест 3 — Safety chain (Phase 3, до первого боевого)

1. Собрать щит полностью, **но вместо ТЭНа — лампа накаливания 100 Вт в патроне** (через клеммы ТЭНа).
2. Подать 230 В на щит, включить контактор через UI (Tests → ESP→enable → ON).
3. На экране Run задать heater = 100 % → лампа загорается на полную яркость.
4. **Тест E-stop**: нажать грибок → лампа **гаснет МГНОВЕННО** (<1 сек, по сути 1 цикл AC ≈20 мс). Отпустить грибок, заново активировать enable из UI → лампа снова горит.
5. **Тест биметалла**: прогреть KSD9700 феном/зажигалкой до >110 °C → лампа гаснет. Остудить → размкнутый контакт обратно замкнётся, но enable-relay уже отжат safety-логикой ESP, надо включить заново из UI.
6. **Тест термопреда**: **НЕ ТЕСТИРОВАТЬ грубо** — он одноразовый. Просто прозвонить мультиметром в холодном состоянии (должен звонить, R<1 Ом).
7. **Тест watchdog (потеря связи)**: отключить Wi-Fi на роутере или выключить Pi на 60 сек → через ≤30 сек ESP должен сам отжать enable-relay → лампа гаснет, пищалка пищит. Включить обратно, в UI должно показать аварию в логе.

**Прохождение**: каждое размыкание гасит лампу за <1 сек, watchdog срабатывает за ≤30 сек.

#### Тест 4 — Slow PWM ТЭНа под нагрузкой (Phase 3)

1. С лампой 100 Вт вместо ТЭНа задать из UI мощность:
   - 25 % → лампа коротко вспыхивает раз в ~2–3 сек, основную часть периода погашена
   - 50 % → симметричные on/off с равными интервалами
   - 75 % → длинные импульсы on, короткие off
   - 100 % → постоянное свечение
   - 0 % → погасла
2. Замерить мультиметром (True-RMS, если есть) средний ток через лампу при 50 % → должен быть ~½ номинального.

**Прохождение**: ШИМ визуально и метрологически работает.

#### Тест 5 — Тепловой тест SSR (Phase 3, перед боем)

1. Подключить **реальный ТЭН**, налить полный куб **воды** (без браги!).
2. В UI задать мощность 100 %, контактор ON.
3. Каждые 5 минут замерять температуру корпуса SSR ИК-термометром или контактным термопаро-мультиметром.
4. Через 15 минут полной нагрузки **температура SSR должна стабилизироваться ≤ 80 °C** при окружающей 25 °C (т.е. ΔT ≤ 55 °C).
5. Если SSR > 80 °C через 15 минут — **выключить, добавить радиатор крупнее или вентилятор**. Не пытайтесь работать на пределе.

**Прохождение**: T корпуса SSR ≤ 80 °C на полной мощности в течение часа.

#### Тест 6 — Алгоритм потстила «на воде» (Phase 4)

1. Реальный ТЭН, реальные клапаны (вода течёт реально через обратный холодильник), куб с **водой** (без браги).
2. В UI запустить режим «Потстил» с параметрами как для дистилляции (T_start=80, T_body=85, T_stop=99).
3. Проверить, что система проходит фазы:
   - HEAT_UP: heater=100 %, клапан воды открыт, клапан узла отбора ЗАКРЫТ (total reflux), ждём пока T_kub дойдёт до 80
   - DISTILLING (для потстила вся фракция в один приёмник): heater=p_work, клапан узла отбора ОТКРЫТ постоянно (потстил = без выделения голов/тела/хвостов), просто сольёт горячую воду в продукт-приёмник
   - SHUTDOWN: при T_kub > 99 → heater=0, клапан узла отбора closed, через 60 сек клапан воды closed, пищит, сессия закрыта в БД
4. Записать в `docs/calibration.md` фактические времена и поведение для будущей подстройки.

**Прохождение**: все фазы пройдены автоматически, переходы корректные, finалом — safe state.

#### Тест 7 — Симуляция аварий в работе (Phase 4)

С работающим режимом потстила на воде:
1. **Выдернуть провод DS18B20 куба** → через 5 сек (3 чтения подряд с ошибкой) ESP уходит в safe state, в UI авария «Sensor T_kub lost», пищалка. Контактор отжат.
2. **Закоротить провод DS18B20 куба** (фаза → DQ на 1 сек) → 1-Wire CRC error → ESP игнорирует на 5 сек, потом safe state.
3. **Закрыть кран водопроводной воды** на входе в линию охлаждения → нет потока. Расходомера нет ⇒ обнаружим косвенно: `T_water_out` растёт ненормально. Тестим: T_water_out >50°C → warning, >65°C → автоматическое снижение мощности на 50 % (см. 7.4 tripwire).
4. **Отключить Pi от сети** → через ≤30 сек ESP watchdog → safe state.

**Прохождение**: все аварии корректно регистрируются и приводят в safe state.

### 13.3 Чек-лист перед первым «боевым» запуском с брагой

- [ ] Все 7 dry-тестов пройдены, лог в `docs/dry_test_results.md` с датой и фактическими цифрами
- [ ] Силовое заземление проверено: R < 1 Ом между корпусом ТЭНа/куба и PE-шиной щита
- [ ] УЗО проверено кнопкой TEST → размыкается за <30 мс
- [ ] Радиатор SSR ≤ 80 °C после 60 минут полной нагрузки
- [ ] Все винтовые клеммы протянуты после первого включения (медь «садится» на ~5 % за первый прогрев)
- [ ] Снаббер RC установлен на клеммах ТЭНа
- [ ] Все DS18B20 откалиброваны в кипящей воде и ледяной воде, offset сохранён в БД
- [ ] BME280 показывает разумное давление (1000–1030 hPa)
- [ ] Watchdog работает: тест отключения Pi на 60 сек
- [ ] Telegram-уведомления (если настроены) приходят на «start», «stop», «авария»
- [ ] Первая сессия записана в БД с полным графиком
- [ ] **Огнетушитель углекислотный или порошковый ≥2 кг рядом с установкой**
- [ ] **Вентиляция в помещении** (открытое окно или вытяжка) — пары спирта горючи
- [ ] **Никого не оставляйте установку без присмотра в первые 5 сессий**
